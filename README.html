JCRGM Compassion & Welfare
Support Team register · assistance applications · Supabase setup

Five new files, plus a three-tile “Compassion & Welfare” group added to index.html. Drop all five next to index.html in the GitHub repo and the feature works immediately — no build step, no dependencies, no npm.

Try it right now, before touching Supabase

Open jcrgm-support-team.html on a phone. Everything works offline against the phone’s own storage: the public application form, the reference number, the status lookup, the admin desk. Records queue for upload and sync the moment the database is connected. Nothing is lost while you decide on hosting.

1. Files

  • jcrgm-support-team.html — the portal: home, apply wizard, status lookup, admin desk.
  • jcrgm-support-team.js — the portal’s behaviour: wizard, register, drawer, desk gate. Every write it makes is confirmed against the server before the screen claims success.

  • test/, .t/ — the test suites (not needed on the server; delete or .gitignore before committing if you prefer).

The portal is not a separate app. It loads the four files the rest of the app already ships — church-platform.css, supabase-config.js, vendor/supabase.js, church-platform.js — in that order, exactly as announcements.html does. So it shares one project, one sign-in session, one member list, one realtime socket and one design system. It does not download anything from a CDN, which matters on a phone using the PWA on limited data.

2. Supabase — already decided, one step left

Nothing to create and no key to paste. Your repo’s supabase-config.js already points at https://yisfzexlbjeoeujvmmno.supabase.co with a publishable key, and that is what the welfare pages read. The only missing piece is the table itself:

  1. Open that project → SQL Editor → New query.
  2. Open supabase-schema.sql, select all of it, paste, Run. Expect “Success. No rows returned”.
  3. Reload the portal. The masthead pill should read “Live — supabase-config.js”. If it reads “On this device”, the config file was not found beside the page — check that you committed all five files into the same folder as index.html.

The script is idempotent (every object is create or replace / if not exists), so re-running it after an upgrade is safe and no data is dropped. It also create table if not exists church_members only as a guard so the script still completes on a bare project — in yours that table already exists and is left alone.

Want welfare in its own database instead? Fill supabaseUrl / supabaseAnonKey in jcrgm-config.js. Those two override the shared project, and the church sign-in gate then has no meaning for this portal (it would be checking a different project’s member list), so set requireChurchAuth: false to fall back to the code alone — or keep it true and accept that the desk and the data live in different places. Running supabase-schema.sql in both projects keeps the RPCs valid.

What protects the data

Row-level security is enabled and forced in the schema, and anon has no SELECT on the table at all. A phone can only (a) submit a case through jcrgm_create_case() and (b) read one case back through jcrgm_lookup_case(ref, last4_of_phone), which masks the name as “Chanda M.”. Reading the register needs an authenticated account whose row in church_members is approved and in a Support Team role — the very table church-platform.js reads for Announcements and programme prep, so there is still exactly one list of people with access to the church app:

create policy "jcrgm desk read" ... using (public.jcrgm_is_desk());
create policy "jcrgm desk delete" ... using (public.jcrgm_is_leader());  -- leaders only

Check it yourself after deploying:

# expect 401/403 or an empty array, never the data
curl "https://yisfzexlbjeoeujvmmno.supabase.co/rest/v1/jcrgm_welfare_cases?select=*" \
     -H "apikey: PUBLISHABLE_KEY" -H "Authorization: Bearer PUBLISHABLE_KEY"

Never paste a service_role or sb_secret_ key into these files — it bypasses every policy, and jcrgm-config.js now refuses to start a connection that carries one.

3. Opening the desk: church account + team code

Two things, in order:

  1. An approved church account in a Support Team role. Anyone signed out, or signed in as a plain member, is shown “Sign in / request access” and nothing else — the code box never appears. Leaders are let straight through, because a leader already has more access than this desk does. Roles are set by a leader in Announcements → Manage member access.
  2. The team code (JCRGMST today) for non-leader team members, as a second factor against a shared or left-open phone. It is stored only as a salted SHA-256 digest:
adminPasswordPepper: "jcrgm-welfare-v1",
adminPasswordHash: "0dbe76dc0430264dde5f9a96c14f2d72ce0ad5fe238c853ed456cff8c90b90ef",  // "JCRGMST"
adminSessionMinutes: 40, maxPasswordAttempts: 6,
requireChurchAuth: true,
deskRoles: ["welfare", "diaconia", "leader", "pastor", "administrator"],
allowMembersFullAccess: false, listLimit: 500

If you rename the roles in church_members (say welfare → diaconacy), edit deskRoles here and the role list inside jcrgm_is_desk() in supabase-schema.sql. They are deliberately two copies: the browser check is for politeness, the SQL check is the boundary, and a boundary that silently disagrees with the UI is worse than either alone. The test suite asserts both lists contain welfare and leader.

Rotating the code (when a member leaves the team)

node -e "const c=require('crypto');\
console.log(c.createHash('sha256').update('jcrgm-welfare-v1::NEW_CODE').digest('hex'))"

…paste the result into adminPasswordHash and commit. adminPasswordHashFallback exists only for phones that open the file over file://, where browsers refuse to give the page crypto.subtle; it is ignored whenever real SHA-256 is available.

If you remove church-platform.js from a page

Then the account check cannot run, and the code alone opens the desk — with no sign-in prompt and no crash. That is deliberate: the desk must stay reachable when the platform file fails to load on a poor connection. The database still refuses every read, so a stranger with the code sees an empty register, not other people’s files. The footer of the lock card states which mode is in force (“church sign-in + team code” vs “team code only”).

Be honest about what the code is. Anything a browser can check, a determined person can read in DevTools. The code stops a curious member from wandering into beneficiaries’ NRC numbers on a shared phone — a locked office door, not a vault. The vault is the member list, the RLS policies, and the physical security of the device. Keep it that way by not storing data here that would hurt if leaked (see the privacy note at the foot of the portal).

5. Deploying from GitHub

  • Where they go — the repo root, beside index.html, announcements.html and church-platform.js. Not a subfolder: the portal references its neighbours with relative paths (vendor/supabase.js, supabase-config.js, announcements.html), so a subfolder would break the sign-in bridge and it would lose the shared project.
  • Five new files, one edited — commit jcrgm-support-team.html, jcrgm-support-team.css, jcrgm-config.js, supabase-schema.sql, README.html, plus the modified index.html. Nothing else needs to change; church-platform.*, supabase-config.js and vendor/ are already yours.
  • Offline / PWA — the portal does not register a worker of its own; the app’s single service-worker.js already serves every same-origin .html/.css/.js network-first, so new files arrive on each phone on the next open without bumping anything, and after one visit they are cached for a phone that opens the app with no data. It also refuses to cache anything carrying an authorization header or a query string, so no welfare record is ever written into the browser cache. If you want the portal in the pre-cached set for a first-ever offline launch, add its three files to START_ASSETS and bump VERSION in service-worker.js — optional, and it does not affect correctness.
  • Phones that open the file directly (file://, some WebViews) — crypto.subtle is unavailable there, so the fallback digest is used for the code check and localStorage is the only store. It still works; it simply cannot reach the church database. Serve from the Pages URL whenever you can.
  • Never commit a real Supabase service_role/sb_secret_ key. The publishable key in supabase-config.js is public by design and safe to keep committed — but if a secret is ever pushed, rotate it immediately in Project Settings → API.

6. Data protection notes (Zambia + international practice)

  • Consent is captured, not assumed — the applicant ticks a Data Protection Act No. 3 of 2021 clause, plus a guardian clause that is required whenever the date of birth makes them a minor (the form detects this live).
  • Minimisation — documents are recorded as which items were sighted, not the documents themselves; no ID photographs are stored in the browser.
  • Purpose limitation — internal notes and the applicant-facing decision letter are separate columns, so a staffer’s private assessment cannot accidentally be shown to the applicant.
  • Two-person rule — a case cannot be marked “Assistance Given” without a receipt reference, which the code enforces, not just recommends.
  • Retention — nothing auto-deletes. Run an annual pass: export the year to CSV, then close or delete settled files. The “Full CSV” export includes every column so a deleted year can still be reconstructed for the auditors.
  • Right to be informed — the home tab states plainly that names and photographs are never published without written consent.

(.t/ needs npm install once, for jsdom. The harness serves the folder over http://127.0.0.1:<port> rather than file://, because browsers refuse localStorage on an opaque origin — and it pulls church-platform.js, supabase-config.js and vendor/supabase.js from the repo, so the integration is tested with your real platform files, not a stub.)

  • test/jcrgm-engine.test.js — reference numbers and their check letter (cross-checked against the Postgres algorithm and fuzzed over 20,000 random and all 10,000 sequence values), phone/NRC validation, money, age and minor detection, CSV quoting, XSS sanitising, roll-ups, the offline store, the admin digest, the guard-rails on the Supabase URL and key, the shared-project inheritance from window.JCRGM_SUPABASE, all nine desk-permission cases (member / leader / unapproved / signed-out / platform-missing / platform-half-loaded), and the schema’s own integrity: every public.fn() the policies call must exist, RLS must be enabled and forced, the policies must key off church_members, and anon must hold no SELECT.
  • .t/ui-e2e.js — loads the real page in jsdom and clicks through it, including a whole submission and a reload: blank form refused, each wizard step validated, bad email blocked, minor warning shown, reference issued, status lookup found and denied for the wrong phone, lookup answered from the device when the network is down, the badge counting without waiting on the server, all six register sections filled and re-read, decision letter persisted, disbursement blocked without a receipt, CSV export fired, an injected <script> proven inert — and the platform integration: window.Church present, this portal sharing the platform’s single client rather than minting a second one, the sign-in card replacing the code box when nobody is signed in, the code alone refused, the desk opening only on account plus code, and the desk still reaching the code box when the platform file is missing.
  • .t/sql-check.js — splits supabase-schema.sql the way psql does and parses every statement with the real PostgreSQL grammar (libpg_query, via pglast), because the Supabase editor runs it one statement at a time and a failure in statement 30 of 42 leaves the table created with no policies attached. It also greps for the things a parser cannot see: bitand( and other Redshift/Oracle spellings (legal syntax, unknown function at run time — the exact bug this file had), every referenced public.fn() existing, each policy having a matching drop policy if exists so re-running is safe, force row level security being present, and no SELECT grant to anon. Its limit is stated in the script: it does not read inside AS $$ bodies (libpg_query’s plpgsql entry point rejects RETURNS TRIGGER, and wrapping a LANGUAGE sql body in a DO block invents errors), so the logic of jcrgm_next_ref() and jcrgm_lookup_case() is checked instead by the engine suite, which re-implements them from the SQL text and compares real outputs — a stronger test than a parse. If pglast is absent the SQL check says so and skips; it never pretends to pass.
  • .t/html-check.js — also proves that every class written into the markup is declared in jcrgm-support-team.css or church-platform.css, and .t/ui-e2e.js repeats the check against the live rendered DOM (so a class assembled at runtime is caught too, and only classes that never appear are excused). This found two phantom classes — an identity-chip button and the default toast kind — that would have rendered as unstyled, unobtrusive HTML with no error anywhere. Markup tests are scoped to literal class="…" attributes; the DOM pass is what covers the rest, and the checker says so rather than implying full coverage.
  • .t/html-check.js — quote-aware tag balance, duplicate-id scan, every getElementById/$("#id") resolves, new links exist, tiles in the right place in the header nav, no hard-coded contact details, the six script/stylesheet includes present in the app’s own order, no CDN or third-party reference anywhere, both Supabase constants left blank, and the privacy note matching what the code does.

Where the tests found real bugs during the build

Not style nits — behaviour: the record cleaner was dropping ref_no and id on write, which made every status lookup miss; the reference was truncated to 24 characters, deleting the check letter; the date-of-birth handler re-rendered the step and wiped the date just typed; currency was required but never pre-filled, so “Continue” appeared broken; phones were only normalised on blur, so a user who tapped Continue straight away saved a number that could not be matched later; the JS and SQL check letters both indexed a 24-letter alphabet modulo 26, so roughly one reference in thirteen came out as JCRGM-2026-8010- with no check letter at all — and the harness could not see it, because it duplicated the same wrong constant instead of reading it from the schema (it now parses the alphabet out of the SQL, so the two cannot drift); checkboxes had no name attribute; collapsed register sections removed their inputs from the DOM, making validation errors unfixable; a guard flag permanently silenced the “awaiting” badge; a delete policy called jcrgm_is_leader(), which no CREATE FUNCTION in the script ever defined (that would have aborted the SQL editor run halfway); the desk stayed open forever in single-factor mode because the idle re-check only ran in church mode; and the register painted nothing until DB.list() answered, which on a hung connection means a blank screen for half a minute.

The last two were only found once the portal was wired to the real platform files. A stub would have passed.

8. “Nothing is happening” when the desk closes, saves or deletes a case

This is almost never a broken button. The desk’s buttons talk to PostgREST, and PostgREST has a particular habit that used to make this look like a dead UI: when row-level security (or a missing GRANT) filters a write out, it answers 204 No Content with zero rows and no error at all. Nothing was written, yet nothing failed either. So the page said “Case saved”, re-read the list, and the row quietly snapped back to what it was — exactly “nothing is happening”.

The code no longer trusts a write it cannot see. Every update asks the server for the row back (update(…).select()) and counts only what returns; every delete is confirmed the same way before the file is removed from the device. If the database did not accept it, you now get:

  • a red toast headed “Not written to the database” (or “Not deleted”) that names the reason;
  • the attempted change stays visible on the row, marked Not written, instead of reverting, so the desk never loses track of what it typed;
  • a banner above the register — “n change(s) are on this phone only, the database did not accept them” — with a Retry button that re-sends them the moment access is fixed. No re-typing.

If the register itself cannot be read, the banner says so plainly (“This is the copy on this phone”) instead of showing a stale list as though it were live.

The two causes, and how to tell which one you have

  1. The signed-in account is not on the Support Team. Roles come from church_members.role, which the church app sets in Announcements → Manage member access. A member or an unapproved account can file an application but cannot amend the register — by design. The code alone does not open the desk any more: with the right code and the wrong account you get “Right code, wrong account”, because the database would refuse the write anyway.
  2. supabase-schema.sql was run only partly. The tables can exist while the grants, functions and policies do not, because the script creates them in order and stops at the first failure.

One query that answers “did the schema actually run?”

Paste this in the SQL editor instead of guessing. Every line should come back t:

select
  (select count(*) = 4 from pg_policy p join pg_class c on c.oid = p.polrelid
     where c.relname = 'jcrgm_welfare_cases')                             as all_policies,
  (select count(*) = 4 from pg_proc where proname in
     ('jcrgm_create_case','jcrgm_lookup_case',
      'jcrgm_is_desk','jcrgm_is_leader'))                                 as functions,
  (has_table_privilege('authenticated','jcrgm_welfare_cases','update'))    as can_update,
  (not has_table_privilege('anon','jcrgm_welfare_cases','select'))         as anon_blinded,
  (select count(*) = 2 from pg_proc where proname in
     ('jcrgm_desk_roles','jcrgm_leader_roles'))                            as role_lists;

An f anywhere means the script stopped part-way: fix the line the editor complained about and run the whole file again. Nothing in it destroys data — create table if not exists, create or replace, and drop policy if exists before each create policy, so a second pass is safe by design. .t/sql-check.js re-reads the four counts above against the script itself, so this query cannot go stale.

Deleting is a leader's decision, on purpose

A desk member may read and amend a case; only a leader may DELETE one — an audit trail a volunteer can erase is not an audit trail. Because a policy-filtered delete arrives as 204 with no rows, the desk no longer fires a doomed request: a welfare or diaconia member is told “Needs a leader” and offered Close case, which keeps the record. The two role lists live once, in the database:

select public.jcrgm_desk_roles()   as who_may_amend,
       public.jcrgm_leader_roles() as who_may_delete;

CONFIG.deskRoles and CONFIG.leaderRoles in jcrgm-config.js mirror them, and test/jcrgm-engine.test.js compares the JS arrays with the schema text and fails if they drift — which matters, because a role the door lets in and the database then refuses is itself a “nothing happened” report.

After re-running the SQL, sign out and back in (or tap ↻ Sync on the desk): the page keeps the PostgREST response for the session, and Retry in the banner will then flush everything it had marked Not written — the unsaved changes are kept in the browser, not lost with the failed attempt.
